# 启动钱包生成与一次性查询设计

## 目标

让 `wallet-scan run` 在启动时可选地生成一组新钱包，并对该组钱包执行一次公开原生余额查询。系统只记录公开地址和每个查询的完整结果，不保存助记词，不根据余额筛选地址，不发送余额通知，也不把这次任务当作既有地址库的长期扫描。

一组钱包包含一个 BIP-39 助记词派生出的四个公开地址：BTC、ETH、Solana 和 TRON。由于 EVM 地址可用于多个网络，实际查询目标为六个：BTC、Ethereum、Arbitrum、BSC、Solana 和 TRON。

## 范围与约束

- 默认在 `run` 服务启动时执行一次；通过 `GENERATE_WALLET_ON_STARTUP=false` 可关闭。
- 每次进程启动最多生成一组，不循环生成，也不自动重试查询。
- 助记词只在生成函数的进程内存中短暂存在，不写数据库、日志、通知、错误信息或 HTTP 响应。
- 数据库保存四个公开地址及其批次 UUID。
- 数据库保存六次查询的成功、零余额、正余额和失败状态。
- 启动任务不写入 `positive_findings`、`notification_events` 或现有扫描运行计数。
- 查询失败必须记录为失败状态，不能转成零余额。
- 启动任务完成或失败后，HTTP 服务继续按原有流程启动；任务错误通过服务日志报告，但日志不得包含助记词。

## 方案

新增独立的启动检查组件，直接依赖已有的 `wallet.Generate`、`providers.Provider`、`adaptive.Limiter` 和 `db.Store`：

1. 生成一个新钱包并立即提取四个公开地址；生成结果离开启动任务函数前不再保留助记词字段。
2. 使用新的批次 UUID 将四个地址插入 `wallet_addresses`，标签标记为启动生成地址，并取得每个地址的数据库 ID。
3. 建立六个固定查询目标，将地址 ID、地址类型、链和公开地址绑定起来。
4. 通过现有 provider 和限流器并发执行六次查询，每个目标只调用一次。
5. 将每个结果写入独立的 `wallet_balance_checks` 表。成功结果写入精确的最小单位余额和资产符号；失败结果写入状态、错误码、provider 和错误信息。
6. 任务返回后启动 HTTP server。后续显式执行的旧 `scan` 命令仍按原有行为处理导入地址，不由启动检查自动触发。

直接调用 provider 是推荐方式：避免服务启动时通过 HTTP 自调用，保留精确的 provider 错误信息，并能复用已有的限流实现。启动任务不调用 `Scanner.RunOnce`，因为该方法面向地址库的全量持久化扫描。

## 数据模型

新增 `wallet_balance_checks` 表：

- `id`：自增主键。
- `address_id`：关联 `wallet_addresses.id`，地址删除时级联删除查询记录。
- `chain`：六个受支持的链之一。
- `state`：`checked` 或 `retry`；保留 API/provider 的结果语义。
- `balance_atomic`：成功查询时记录最小单位整数，零余额合法；失败时为空。
- `asset_symbol`：成功查询时记录资产符号。
- `error_code`、`error_message`、`provider`：失败诊断字段，成功时为空。
- `retry_after_ms`：失败结果建议等待时间，可为空。
- `checked_at`：查询完成时间。

`UNIQUE (address_id, chain)` 保证一次批次内每个目标只有一条记录。助记词、私钥、扩展密钥和任何可签名材料不进入数据模型。

为使插入地址后能安全建立外键关系，数据库层新增返回地址 ID 的批量插入方法；现有导入方法的返回值和行为保持兼容。

## 配置与启动时序

配置新增布尔字段 `GenerateWalletOnStartup`，由 `GENERATE_WALLET_ON_STARTUP` 读取，默认值为 `true`。环境变量显式设置为 `false` 时跳过生成任务；非法布尔值使配置加载失败。

`runService` 的时序为：构建 provider 和限流器，按开关执行一次启动检查，记录任务错误，然后启动原有 HTTP server。信号取消会传给生成和查询上下文，避免进程退出时继续发起请求。

## 错误处理

- 生成失败或地址写入失败：任务终止并记录错误，HTTP server 仍启动。
- 单个 provider 查询失败：记录对应失败结果，其他五个目标继续执行；不把失败当作零余额。
- 数据库写入某条结果失败：任务报告错误；已成功写入的结果保留，便于诊断。
- 上游返回空余额或非法余额：按 provider 的错误路径记录失败状态，不写入伪造的零值。
- 任务不调用通知 outbox，因此不会因为查询到正余额产生 WeCom 消息。

## 测试与验收

- 配置测试：默认开启、显式关闭、非法布尔值报错。
- 数据库测试：地址 ID 返回、六类结果可写入、零余额和失败字段正确保存、唯一约束生效。
- 启动任务测试：生成一组地址并恰好发起六次查询；所有结果都会写入，包括零余额和失败；不调用正余额保存或通知接口；助记词不出现在日志和持久化对象中。
- 服务测试：启动任务失败时 HTTP server 仍能启动；关闭开关时不生成钱包。
- 完成后运行 `go test ./...` 和 `go vet ./...`。
